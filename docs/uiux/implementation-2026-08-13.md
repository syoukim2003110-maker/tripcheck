基準は [`design-standard-v3.1.md`](design-standard-v3.1.md)、着手前の差分は
[`gap-2026-08-13.md`](gap-2026-08-13.md)。ここは**実際に何を変え、何を変えず、

## 0. 先に、厳密さの話

「ユーザーはどこまでの厳密性を求めているか」への答えが、この実装の設計判断を
決めました。

**旅行者は二値の事実には厳密で、精度の演出には無関心です。**

- 怒るのは、**着いたら閉まっていた**とき。**予約に間に合わなかった**とき。
  「4日で回れます」と言われて**実際は回れなかった**とき。
- 怒らないのは、滞在が90分か95分かの違い。移動が40分か「約40分」かの違い。
  その数字が「確認済み」か「推定」かの内部区分。

だから実装の方針はこうなりました。

| 対象 | 扱い |
| --- | --- |
| 営業状態・予約・成立判定（二値で、外すと旅行が壊れる） | **エンジンも表示も一切弱めない** |
| 滞在時間・移動時間の確度（連続量で、外れても旅行は壊れない） | バッジをやめ、言葉（「目安」）で運ぶ |

前者は `docs/product.md` の契約そのままです。後者が §2.2 の語彙置換です。

## 1. 写真：入れませんでした（無料枠の絶対条件）

**結論: タイムラインに写真サムネイルは入れていません。従量課金の
リクエストを1件も増やしていません。**

`/api/place-photo` は Places Photo の従量課金経路です（1カード1枚 = 1課金
イベント、ブラウザキャッシュ15分）。停留所ごとにサムネイルを出すと、
**旅程を開くたびに「表示中の日の停留所数」だけ課金イベントが増えます**。
1日5か所・4日を一巡すれば20件、日を切り替えるたびに再発生します。
「無料枠を絶対に超えない」という条件下で、これは選べません。

代わりに、参照画像の視覚的リズムを**課金ゼロの手段**で作りました。

- 停留所のマーカーを**その日のデイカラー**にしました（`ItineraryTimeline` が
  開いている日の色を `--day-color` として配下に配り、`.planner-stop-dot` が
  それを使う）。**地図のピンとタイムラインの番号が同じ色・同じ番号**になり、
  「Apple Maps らしさ」の核である地図↔旅程の対応が、写真より強く出ます。
- 日タブをデイカラーの塗りピルにしました。
- 移動をカード化し、行間・文字サイズを上げました（§3）。

**副次的に写真の支出は減りました。** 詳細シートの根拠を `<details>` に
入れたため、閉じた状態では中の `<img>` がリクエストを出しません。
以前はシートを開いた瞬間に場所写真を1枚買っていたのが、いまは
「営業時間・根拠を見る」を開いたときだけになります。

### 報告事項：現在の上限は「無料枠の保証」になっていません

調べたついでの発見です。`lib/server/provider-cost-policy.ts` の月次上限を
Google 分だけ合計すると **137,000 イベント/月** です。

| operation | maxPerMonth |
| --- | ---: |
| live_routes | 20,000 |
| place_suggestions | 30,000 |
| place_photo | 30,000 |
| food_recommendations | 20,000 |
| place_resolution | 12,000 |
| place_intelligence | 10,000 |
| route_recommendations | 9,000 |
| hotel_recommendations | 6,000 |
| **合計** | **137,000** |

これは「暴走を止める天井」であって、無料枠に収める設計ではありません
（実使用がゼロに近ければ実害はありませんが、**上限は守ってくれません**）。
実際の無料枠の枠数が分からないと安全な値を決められないので、
**この数字は変更していません**。下げるなら、SKU ごとの無料枠を教えて
いただければ、そこから逆算した上限に書き換えます。

## 2. 評価★・「営業中」：出さないのが正解

参照画像は推薦カードに「4.6★（512件）・営業中」を出しています。
Anchor（利用者自身が入れた場所）にも出すかを判断しました。

| 対象 | 判断 | 理由 |
| --- | --- | --- |
| **Anchor の評価★** | **出さない** | 利用者はもう選び終わっています。自分で選んだ清水寺に「4.2★」と出しても、できるのは選択を後悔することだけ。`docs/product.md` の原則1「発見フィードにしない」に真っ向から反します |
| **Filler（TripCheck の提案）の評価★** | **出す（実装済み）** | こちらは利用者が選んでいないので、信じる理由が要ります。`MealRecommendationCard` / `GapRecommendationCard` は実データがあるときだけ出しています |
| **「営業中」（現在の営業状態）** | **旅程画面には出さない** | 旅行は先の日付です。「いま営業中」は旅行日について何も言っていません。意味があるのは**その日**の事実（「その日休み」「最終入場後」）で、それは既に実装済みかつ Tier A です |

**結果としてこの判断は課金ゼロです。**「出さない」が答えなので、新しい
取得が要りません。

## 3. 実際に変えたもの

### 3.1 根拠の受け皿（前提）

`StopInspector` に **「営業時間・根拠を見る」** と **「この場所の条件を変える」**
の2つの開示を新設。前者に滞在時間の確度・営業時間・取得元・写真・分析を、
後者に滞在時間と最終入場の編集を入れました。

- **参照画像と1点だけ違えています**: 参照は「予定から外す」を根拠リンクの
  上に置いていますが、TC-053 §9.2 は破壊的操作をパネル最後の対話要素に
  固定します。誤タップの実害の方が、モックとの一致より重い。
- 「日を移動」は開示に入れず表面に残しました。旅行者が実際に使う調整は
  こちらだからです。

### 3.2 語彙（Tier B / C）

| 変更 | 前 | 後 |
| --- | --- | --- |
| 滞在時間の確度 | 「滞在90分」＋`推定`バッジ | **「滞在の目安 1時間30分」**（確定時は「滞在 1時間30分」） |
| 判定コードの見出し | 「条件付き」＋見出し文 | 見出し文のみ。状態は文の横の色付きマークが持つ |
| 未確認の件数 | 「未確認の重要情報が10件あります」 | **「インターラーケンほかは出発前の確認が必要です。」** |
| 空の推薦枠 | 高さ125pxの提案ボックス＋弁明文＋ボタン | **1行＋横のボタン**（枠の Filler ラベルは残す） |

「未確認…10件」は、その下の「確認したいこと **2**」と**同じ心配を違う数え方
で二重に出して**いました（片方は事実の数、片方は行動の数）。どちらも旅行者に
できることを言っていません。場所を名指しし、数を捨てました。

### 3.3 密度（§4.3 / §4.4）

`app/planner.css` の全面パス（`@media print` は除外）。

| 項目 | 前 | 後 |
| --- | --- | --- |
| `font-size` の12px未満 | **258 / 374件（69%）** | **0件**（ラベルの11pxのみ、印刷は別） |
| 10px未満 | 61件 | 0件 |
| `border-radius` の異なり値 | 15種 | **3種**（10 / 14 / 999） |
| 結果見出し（≥841px） | 22px | **34px** |
| 停留所名 | 14.5px | **17px** |

**余白は全面正規化していません。** 4px刻みへの一括置換は、得られる見た目の
差に対して壊す範囲が広すぎます。v3.1 が触れた面（タイムライン行・カード・
シート）で個別に整えました。基準 §4.4 の記述はこの実態に合わせて直してあります。

### 3.4 構造（§6.2）

見出しと日タブの間にあった**タイルを廃止**しました。

- 「旅程の結論」ラベル（見出しが既に言っている）→ 削除、`aria-label` に移動。
- 最短日数の計算根拠（「09:00–22:00・拠点…・移動ごと10分の余白では、最短3日です」）
  → **「結論の詳細」の中へ**。`docs/product.md` は「根拠は旅程の下」と
  定めているので、本来の置き場所に戻した形です。
- 直すものが無いプランからは行動ボタンも消えました（旧実装の
  「このプランを見る」は真下の日タブへスクロールするだけでした）。
- 残ったのは**警告1行とその行動1つ**、そして下端の罫線だけ。

### 3.5 タイムライン（§5.1 / §5.2）

- 停留所マーカー = デイカラー（地図ピンと一致）。
- 移動が**カード**に：手段マーク／「電車 95分・乗換1回」／**区間（A → B）**／
  シェブロン。区間と乗換回数はこれまで `aria-label` と開示の中にしか
  ありませんでした。
- 日タブ = デイカラーの塗り／輪郭ピル。番号バッジは廃止（「1日目」が同じ
  ことを別の字で言っていた）。**390pxで4日ぶんが横スクロールなしに収まる**
  ようになりました。

### 3.6 入力画面

- 主 CTA を**赤**に（v1.1 の黒を上書き）。固定表示なので、背景色のハローと
  浮きの影を足して「本文の上に着地した箱」に見えないようにしました。
- **ステッパーの非表示は試して戻しました。** 参照画像の入力画面にステッパーが
  無いことを根拠に「最初の一歩では出さない」を実装しましたが、
  `tests/rendered-html.test.mjs` が落ちました。テストを直す前に理由を検算した
  結果、**根拠の方が弱い**と判断しています——参照画像には場所の確認ステップ
  自体が無いので、「ステッパーが不要」の証拠になりません。そしてこの鋲は
  初回訪問者に「この流れは短い」と伝える唯一の要素です。既存テストは正しく、
  変更は取り消しました。

### 3.7 ついでに直った実バグ：Resolve の候補ボタン

候補の選択肢が**幅78px**で描かれていました。スイスの住所が1行あたり数文字で
折り返し、1つの候補が300px超の縦長ブロックになっていました。原因は、
候補の質問が優先度ピッカーと削除ボタンと同じグリッド行を分け合っていたこと。
**確認待ちの行では質問が行全体を使う**ようにしました。

| | 前 | 後 |
| --- | ---: | ---: |
| 候補ボタンの幅 | 78px | **300px** |
| 候補ボタンの高さ | 142–156px | **46px** |
| 質問ブロックの終端（390px, en） | 815px（契約844、余裕29px） | **592px（余裕252px）** |

v3.1 の文字拡大がなければ気づかないままでした（拡大後は1268pxになり
Gate E が落ちた）。

## 4. 仕様変更（`docs/product.md` 反映済み）

既存テストを1件も緩めていないのは、**弱い根拠の変更を1つ取り消したから**でも
あります（§3.6 のステッパー）。テストが落ちたときに直す先はテストとは限りません。

| 変更 | 理由 | 影響した既存テスト |

**既存テストの削除・緩和はゼロです。**

## 6. 空いた時間を埋める（2026-08-14 追加）

「余った1日を使って、あとここと、ここに行けます」への実装です。

**問題**: `assessTripFit` は前から「この希望なら3日で足ります」と言えていました。
統計行も「1日分の空き」と出していました。**それで終わりだった**のが問題です。
1日6時間空いている日に、製品が出せる提案は**1件**でした。診断だけして治療しない。

**原因は定数**: `addRouteRecommendation` の `acceptedMicroFillers >= 1`。
1日あたりの提案上限が、その日の空き時間と無関係に1で固定されていました。

**直したこと**:

| | 前 | 後 |
| --- | --- | --- |
| 1日の提案上限 | **常に1** | **その日の余裕から**（`dayFillerAllowance`: 2時間ごとに1、上限3） |
| タイムラインの提案 | 1件 | 余裕がある日は**最大3件**（2件目以降は「ここも足せます」） |
| パネルの見出し | ギャップの分数だけ | **「この日は6時間25分空いています。あと3か所まで足せます。」**（採用するたび減る） |
| 地図のピン | 1件 | パネルと同じ件数 |

**変えていないこと**（重要）: 採用は1件ずつ、これまで通り**日全体の再計算**を
通ります。hard conflict を作る／Anchor を後ろに追いやる／予約を破る提案は
拒否されます。各カードの「+2時間・余裕 −2時間」は**その時点の旅程に対する**
実測で、1つ採用すると日が組み直され、残りは新しい旅程に対して測り直されます。
食事枠（昼1・夕1）は従来のままです。上限3は、旅行者自身の場所が旅の主役で
あり続けるための天井です。

追加テスト4件（`dayFillerAllowance` の単調性と境界、`spareCapacityLine` の
3状態と「満杯の日は誘わない」）。`docs/product.md` の v0.3 contract に
仕様変更を反映済み。

## 8. やらなかったこと（と、その理由）

- **地図面（凡例カード・縮尺・日セレクタ）**。QA ハーネスは `BASE_URL` 以外の
  リクエストを全部落とすので、**Google Maps はそもそも描画できません**。
  見えない面のレイアウトを勘で変えるのは、前回のパスで一度やって revert した
  過ちと同じです。CSP `script-src` を検証できないのと同じ理由で、ここは
  本番での確認が先です。
- **入力欄のチップ化**。入力欄の設計は 2026-08-13 に別途決めた事項
  （検索窓化）で、同じ日にこちらの判断で上書きするのは筋が違います。
- **日数セレクタの4択化**。参照画像は3日/4日/5日/未定ですが、TripCheck は
  1〜14日を扱います。モックに合わせると機能が減ります。
- **入力画面の旅程プレビューの作り込み**。現在の抽象イラスト＋実在の判定文
  （「4日なら、無理なく回れます / 8か所・移動8時間40分・余裕4時間10分」）は、
  参照画像のプレビューが持つ情報を**捏造せずに**出している版です。
- **モバイルの見出しは17pxのまま**。390pxのファーストビューの予算は旅程に
  使うべきで、参照画像のモバイル画面にはそもそも判定文がありません。
