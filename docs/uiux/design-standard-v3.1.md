# TripCheck UI/UX 基準 v3.1（規範）

出典: `source/TripCheck_UIUX_Final_Handoff_Spec_v3.1.md` と参照画像4枚
（2026-08-13 受領）。この文書は受領物を TripCheck の実際のトークン名・
コンポーネント名・ファイルに翻訳したもので、実装とレビューはこちらを引用します。

受領物の一文を、判断に迷ったときの基準として先頭に置きます。

> The engine can be extremely complex. The experience must feel extremely simple.

実装の記録と、そこで下した判断（写真・評価★・やらなかったこと）は
[`implementation-2026-08-13.md`](implementation-2026-08-13.md)。

## 1. 何を作っているのか

TripCheck は**旅行コンシェルジュ**であって、分析ツールではありません。
利用者は「計画する」のではなく、**すでに出来上がった旅程を確認して調整する**。

- 入力は「行きたい場所」だけ。
- 出力は、何日目・順番・経路・拠点・食事・カフェ・寄り道まで**揃った状態**。
- 画面の主役は **Timeline**。**Map は理解を助ける companion** であり、
  旅程を置き換えません。
- 推薦は検索結果ではなく、**旅程の穴を埋めて完成させるもの**。

この4点は受領物の Core Experience / Visual Direction をそのまま採ったもので、
以下のすべてのルールはここから導いています。

**これは「見た目を似せる」指示ではありません。** TripCheck の内部エンジン
（実現性判定・決定論スケジューラ・hard constraint 管理・推薦ランキング）は
強い状態にあり、v3.1 はそれを一切弱めません。変えるのは、その強さが
利用者にどう見えるか、です。

## 2. 「複雑さを隠す」の正確な意味

受領物の Design Principles はこう書いています。

> Internal: API / evidence / provider / calculation details should stay hidden.

一方で TripCheck の価値は「現実に成立する旅行を作ること」であり、
`docs/product.md` は「不明な営業時間は conditional proposal であって
verified claim ではない」と定めています。**根拠を消すと、製品は自分が
知らないことを知っているふりをすることになります。**

受領物自身がこの矛盾を解いています。参照画像 `04-mobile-three-screens.jpg`
の詳細シート最下部に **「営業時間・根拠を見る ›」** があります。
つまり **隠すのではなく、格下げする**。根拠は一手先に置く。

### 2.1 三層の開示ルール

すべての利用者向け情報は、次のいずれかに分類します。分類のない情報を
画面に出してはいけません。

**Tier A — 通常画面に出す**（利用者の行動が変わるもの）

| 情報 | 出し方 |
| --- | --- |
| 成立判定の結論 | 一文の見出し（「4日なら、無理なく回れます」） |
| 旅程の全体量 | 一行（か所数・移動・余裕）。余裕は緑 |
| 今いちばん重要な警告 | 1件だけ、1回だけ（`product.md`: "states its one warning once"） |
| 各日の量 | 日ヘッダーの2数字（か所数・余裕） |
| 停留所の hard な状態 | その日休み／最終入場後／予約に遅れる = 行の状態として言葉で |
| Anchor と Filler の区別 | 常時。TripCheck の提案を利用者自身の場所と混同させない |
| 推薦の動線コスト | 「動線 +4分」 |
| 採用したときの帰結 | 「余裕 -45分」＋取り消し（参照画像 03 のトースト） |

**Tier B — 詳細シート／1操作先に格下げする**（消さない）

| 情報 | 移動先 |
| --- | --- |
| 滞在時間の確度（推定／確認／指定） | §2.2 の語彙置換に変換。バッジは廃止 |
| 営業時間の根拠・取得元 | 詳細シートの「営業時間・根拠を見る」 |
| 経路の実測／推定の別 | 地図の情報コントロール内（凡例チップを常設しない） |
| 「日付未定・訪問順のみ」 | ヒーロー下の静かな一行、または詳細シート |
| 最短日数の計算根拠（「09:00–22:00・拠点…・移動ごと10分の余白では、最短3日です」） | 「なぜ？」の開示内 |
| evidence 件数・地域カバレッジ・反実仮想 | 既存の Verdict details のまま（`product.md` 準拠） |
| 保存場所の告知（「この端末に保存されます」） | ヘッダーから外し、フッターか設定へ |

**Tier C — 利用者の語彙から消す**（コード・テレメトリには残してよい）

| 情報 | 理由 |
| --- | --- |
| 「条件付き」等の判定コードのチップ | 見出しの一文が同じことをすでに言っている。二重符号化 |
| 未確認項目の**件数**（「未確認の重要情報が10件あります」） | 10件は「1つの警告」ではない。いまやる価値のある1件を行動として書く。全件は既存の「確認したいこと」に残す |
| 空の推薦枠に付く「おすすめ枠」ラベル | 空の枠は項目ではない。候補が無いなら行ごと出さない（取得失敗の告知は §7.4） |
| provider 名（`〜 API` 形式） | `tests/banned-terms.test.ts` ですでに禁止済み |

### 2.2 不確実性は「バッジ」ではなく「言葉」で運ぶ

これが v3.1 でいちばん重要な変換です。技術バッジを消しても、
**数字が確定値のふりをしてはいけない**。参照画像はこれを普通の日本語で
やっています（`02-plan-desktop.jpg`: 「滞在時間の目安：2時間」、
`04-mobile-three-screens.jpg`: 「滞在 2時間」）。

| 確度 | 現在 | v3.1 |
| --- | --- | --- |
| `estimated`（既定値） | 滞在90分 ＋ `推定` バッジ | **滞在の目安 1時間30分** |
| `verified`（取得済み） | 滞在90分 ＋ `確認` バッジ | **滞在 1時間30分** |
| `user_provided`（利用者指定） | 滞在90分 ＋ `指定` バッジ | **滞在 1時間30分** |

同じ規則を移動にも適用します。

| 出所 | v3.1 |
| --- | --- |
| 経路プロバイダの実測 | 「電車 40分・乗換1回」（`約` を付けない） |
| 推定 | 「電車 約1時間」 |

規則を一文で言うと: **確定していない数値には「目安」「約」を付ける。
確定している数値には付けない。** 付いていないことが確定の主張になるので、
この規則は片方だけ実装してはいけません。実装先は
`lib/presentation/timeline-presentation.ts`（`durationSourceLabel` を
表示文の生成に統合する）。

### 2.3 隠してはならないもの

v3.1 を「簡素化」の許可証として読まないための禁止事項です。

1. **Filler を Anchor と同じ見た目にしない。** TripCheck の提案が利用者の
   希望と見分けられなくなった時点で、旅程は嘘になります。
2. **hard conflict を静かにしない。** その日休み・最終入場後・予約に遅れる、
   は Tier A です。詳細シートに落としてはいけません。
3. **成立しない旅程を成立して見せない。** ヒーローの一文は判定そのものです。
   見栄えのために断定を強めてはいけません。
4. **評価・営業状態・価格を推測で書かない。** 4.6★(512件) はプロバイダが
   返したときだけ。「営業中」はその日その時刻の実データがあるときだけ。
   価格・お得さの表現には実際の価格シグナルが要る（`product.md`）。
5. **写真を根拠の代わりにしない。** 写真は雰囲気であって証拠ではありません。

## 3. 写真

参照画像はすべて写真主導です。TripCheck 側の実態（2026-08-13 実測）:

- パイプラインは**すでにある**。`photoName` / `photoSignature` /
  `photoAttribution`（`lib/route-recommendations.ts`）、署名付き
  `/api/place-photo`（`lib/presentation/place-photo.ts`）、CSP 対応済み。
- **出ている場所**: `MealRecommendationCard` / `GapRecommendationCard` /
  `StopInspector` / `HotelInspector`（外部記事サムネ）。
- **出ていない場所**: タイムラインの停留所行（`ActivityCard`）、ホテル推薦
  カード、Start 画面のプレビュー。参照画像との最大の見た目の差はここです。

**2026-08-13 の決定: タイムラインに写真は入れない。**
無料枠を超えないことが絶対条件である以上、旅程を開くたびに停留所の数だけ
課金イベントが増える設計は選べません（`/api/place-photo` は 1枚 = 1課金）。

参照画像の視覚的リズムは、課金ゼロの手段で作ります。

1. **停留所マーカーはその日のデイカラー**にする。地図のピンと番号も色も
   一致するので、写真より強く「地図と旅程が同じもの」を示せます。
2. 日タブはデイカラーの塗り／輪郭ピル。
3. 行間・文字サイズ・カード化で余白を作る（§4.3 / §5）。

写真を出してよいのは、次をすべて満たすときだけです。

1. **新規の場所検索を起こさない**（ビルド時に取得済みの place intelligence
   から出す。写真のためだけに Places を引かない）。
2. 旅程1件あたりのリクエスト数に上限を持ち、**Gate A の予算に載っている**。
3. **写真が無くても行が壊れない**（既存の `onError` 規約、レイアウトシフト禁止）。
4. `photoAttribution` があるものは詳細シート側で帰属を出す。
5. `alt` は場所名、装飾サムネは `alt=""`。

現状これを満たすのは推薦カード（Meal / Gap）と詳細シートだけで、
そこでは既に出ています。詳細シートの写真は根拠の開示の中にあるため、
**開いたときだけ**取得されます。

## 4. トークン

現行の値（`app/planner.css` `:root`）は**色に関してはほぼ正しい**。
変えるのは主に**適用先**と**タイポ／余白のスケール**です。

### 4.1 色（据え置き）

`--pl-bg #f7f7f4` / `--pl-panel #ffffff` / `--pl-ink #171717` /
`--pl-accent #d63f35` / `--pl-good #157a46` と、7日分のデイパレット
（`#2563EB` `#7C3AED` `#C2410C` `#15803D` `#BE185D` `#0F766E` `#A16207`、
`PLANNER_MAP_DAY_COLORS` と CSS が一致済み）は参照画像と整合しています。
新しい色は要りません。

### 4.2 色の適用（変更）

| 対象 | 現在 | v3.1 | 根拠 |
| --- | --- | --- | --- |
| 主 CTA | `--pl-cta`（黒 #171717） | **`--pl-accent`（#d63f35）** | 参照画像 01 / 04 の主 CTA は赤。**v1.1 の黒 CTA を上書きします** |
| 日タブ | 下線＋9%色地 | **デイカラーの塗りピル**（非選択は同色の輪郭） | 参照画像 02 / 04 |
| 統計行の「余裕」 | `--pl-ink-2` | **`--pl-good`** | 参照画像 02 |
| カードの立体感 | `--pl-shadow`（0 16px 44px / 14%） | **1px `--pl-line` の枠、影なし** | 参照画像は総じて平ら。影は浮遊層だけ |
| 浮遊層（メニュー・シート・トースト） | `--pl-shadow` | 据え置き | |

### 4.3 タイポ

現行は 9.5–14.5px にほぼ全ての文字が収まっており、これが「分析ツール」の
印象の主因です。参照画像は一段大きく、行間が広い。

| 役割 | ≥841px | ≤840px |
| --- | ---: | ---: |
| ヒーロー（結果の一文） | 34px / 900 / -0.03em | 24px |
| 入力画面の見出し | 42px（据え置き） | 32px（据え置き） |
| 旅程統計行 | 15px / 700 | 14px |
| 日ヘッダー | 15px / 800 | 14px |
| 停留所名 | 17px / 750 | 16px |
| 説明文 | 13px / 450 / line-height 1.6 | 13px |
| メタ（時刻・滞在・移動） | 13px | 12.5px |
| ラベル／見出し小 | 11px / 800 / 0.06em | 11px |

**下限規則: 利用者に見せる文字は 12px 未満にしない**（ラベル・
タブラーな単位表記のみ 11px を許す）。現行 CSS には 9.5px / 10px / 10.5px が
多数あり、これは v3.1 の calm/premium と両立しません。

見出しには `text-wrap: balance`、数字が縦に並ぶ箇所には
`font-variant-numeric: tabular-nums`（既存の慣行を維持）。
`--pl-display`（Anton）はロゴとデイバッジ用のまま、本文には使いません。

### 4.4 余白・角丸

- 間隔は 4px 基準の **4 / 8 / 12 / 16 / 20 / 24 / 32**。ただし**一括置換は
  しません**: 得られる差に対して壊す面が広すぎるので、v3.1 が触れた面
  （タイムライン行・カード・シート・結果ヘッダー）から順に揃えます。
- 角丸は **3種類だけ**: `10px`（コントロール）/ `14px`（カード）/
  `999px`（ピル）。2026-08-13 に 15種 → 3種へ統一済み。
- カード内の余白は最小 **12px**、デスクトップのカードは **16px**。
- 兄弟要素の間隔は flex/grid の `gap` で作る（個別 margin の相殺を避ける）。

## 5. コンポーネント

受領物が要求する10コンポーネントは**すべて実在します**。v3.1 は新規の
コンポーネント階層を要求していません。責務の対応表:

| 受領物 | 実装 |
| --- | --- |
| TripSummaryCard | `app/components/planner/summary/TripSummaryCard.tsx` |
| ItineraryTimeline | `app/components/planner/timeline/ItineraryTimeline.tsx` |
| DayTimeline | `app/components/planner/timeline/DayTimeline.tsx` |
| ActivityCard | `app/components/planner/timeline/ActivityCard.tsx` |
| MovementCard | `app/components/planner/timeline/MovementCard.tsx` |
| RecommendationCard | `app/components/planner/recommendation/GapRecommendationCard.tsx`（＋束ねる `TripEnhancementPanel.tsx`） |
| HotelRecommendationCard | `app/components/planner/recommendation/HotelRecommendationCard.tsx` |
| MealRecommendationCard | `app/components/planner/recommendation/MealRecommendationCard.tsx` |
| TripMap | `app/components/planner/map/TripMap.tsx` |
| LocationDetailSheet | `app/components/planner/inspector/StopInspector.tsx`（＋ `HotelInspector` / `MealInspector`） |

したがって v3.1 の作業は**再設計ではなく、既存コンポーネントの
情報量・語彙・寸法の是正**です。新しいコンポーネントを足す前に、
この表のどれかで足りないかを必ず確認してください。

### 5.1 ActivityCard（v3.1 の目標形）

```
[時刻]  ●番号   [写真 64×64 / 無くても可]
                場所名（17px）
                説明1行（13px, 2行まで, 省略）
                🕘 滞在の目安 1時間30分     [状態チップ（あれば）]
```

- 番号バッジはその日のデイカラー。Filler は番号ではなくアイコン。
- 「推定」バッジは廃止し、§2.2 の語彙に統合。
- 状態チップは hard な事実のときだけ（その日休み・最終入場後・予約遅れ）。
- 説明文は place intelligence の要約があるときだけ。無いなら行を詰める。

### 5.2 MovementCard（v3.1 の目標形）

```
[09:15]  [🚆]  電車 40分・乗換1回                    ›
[09:55]        ラウターブルンネン → クライネ・シャイデック
```

現行の「電車・95分」＋「移動手段を変える」リンクを、時刻レンジ・手段
アイコン・区間・詳細シートへの `›` を持つカードに揃えます。手段変更は
詳細シート側の操作に移し、行からリンクを外します。

## 6. 画面別の目標

### 6.1 入力（Start）

参照画像 `01-start-desktop.jpg` / `04` 左。**現状がいちばん近い画面**です。
見出し・サブコピー・左入力＋右プレビューの構成は一致済み。差分:

1. 主 CTA を赤に（§4.2）。
2. 場所入力を**チップ入力**へ（確定した場所は `×` 付きチップになる。
   現在は素のテキストエリア）。貼り付け・1行1か所は維持。
3. 右プレビューを**具体的な旅程プレビュー**へ（日番号＋宿泊＋昼食の行、
   ミニ地図、写真4枚）。現在の抽象イラストを置き換えます。
4. ステッパー（1 場所と日数 → 2 旅程）を外し、ヘッダーは
   ロゴ＋補助リンクだけにする。

「5秒で理解できる」が受け入れ基準です。技術説明・内部設定・複雑な
オプションは既定パスに出しません（既存の custom path はそのまま）。

### 6.2 結果（デスクトップ）

参照画像 `02` / `03`。ファーストビューの順序は
**ヒーロー一文 → 3つの事実 → 日ピル → 最初の2停留所**。
現在ヒーローと日タブの間にある **feasibility カードと警告バンドを
どかす**のが最大の構造差分です（「なぜ？」の開示と「確認したいこと」へ）。

- 2カラム（旅程 48% / 地図 52%）は維持。
- 推薦は**第3カラム**として ≥1280px で開き、1024–1279px では地図に重ね、
  モバイルではボトムシート（参照画像 03）。現在のインライン展開を置き換えます。
- 左のアイコンレール（参照画像 02）は任意。入れるなら現行のヘッダー機能の
  移設であって、新しい情報の追加ではありません。

**Gate E との関係**: v3.1 はファーストビューの要素を**減らす**方向なので、
既存契約（モバイル first stop y≤300 / デスクトップ y≤360、実測 297 / 352）
と衝突しません。むしろ余裕が増えます。文字を大きくする分は、
バンドを外した分で吸収します。

### 6.3 結果（モバイル）

参照画像 `04` 中央・右が、現行の設計を**追認**しています:
旅程と地図は上部タブでの二択で、旅程側に地図バンドを持たない。
`product.md` のモバイル契約はそのまま有効です。差分:

- タブは現行のフローティングトグルではなく、**ヘッダー直下の下線タブ**
  （旅程 / 地図）。
- 旅程の末尾に「ルートを地図で確認 ›」のプレビューカード。
- 地図タブの詳細シートは、番号バッジ・予定時刻・滞在時間・
  前後スポット移動・「予定から外す」・**「営業時間・根拠を見る ›」**。
  最後の1行が §2 の格下げ先そのものです。

### 6.4 詳細シート（LocationDetailSheet）

Tier B の**受け皿**。ここが弱いと §2 の格下げが「隠蔽」になります。

必須: 写真／場所名／予定時刻と滞在時間／その日の移動（前後スポット）／
予定から外す／**営業時間・根拠を見る**。

**参照画像と1点だけ違えます。** 参照は「予定から外す」を根拠リンクの上に
置いていますが、TC-053 §9.2 は破壊的操作をパネル最後の対話要素に固定します。
誤タップの実害の方がモックとの一致より重いので、TC-053 が勝ちます。
根拠の内側には、営業時間の取得結果と取得元、滞在時間の確度、
経路の実測・推定の別を置きます。

### 6.5 地図

`product.md` の地図契約（1日1色・番号付き Anchor ピン・Filler/食事/ホテル/
警告ピンの区別・選択5px/非選択2px・双方向選択・欠損ジオメトリは描かない）は
そのまま有効で、参照画像とも一致しています。v3.1 が足すのは:

- 凡例を**常設チップの帯ではなくカード**に（参照画像 02: 移動（電車）／
  ハイキング・散策／その他の交通）。
- 「実経路／推定」の別は凡例カードの中へ（Tier B）。
- 縮尺バー。
- 「1日目のルート」のような**日セレクタ**を地図自身に持たせる。

## 7. 推薦の見せ方

### 7.1 共通

推薦は検索結果ではなく**旅程を完成させる部品**です。カードは必ず
「なぜこれか」を持ちます。

必須要素: 写真／名前／**動線コスト（「動線 +4分」）**／評価（あるときだけ）／
営業状態（実データがあるときだけ）／一文の理由／採用ボタン。

### 7.0 空きは、名指ししたら埋められるようにする

判定が「この希望なら3日で足ります」と言えるなら、製品は**その空きに何を足せる
かまで**言わなければなりません。空きを名指しして提案が1件では、診断だけして
治療しないのと同じです。

- 1日が受け取れる提案の数は、**その日の余裕から**決めます
  （`dayFillerAllowance`: 余裕2時間ごとに1、上限3）。定数の1ではありません。
- 推薦面は**その日の空き時間と、あと何か所足せるか**を言い、採用のたびに減ります。
- 余裕が1か所ぶんの日は、これまで通り「既定1件＋代替2件」（=1枠への選択肢）。
  余裕がある日は**3件を並べます**（=全部足せる別々の停留所）。
- 上限3は天井です。**旅行者自身の場所が旅の主役**であり続けるために要ります。
- 採用は1件ずつ、日全体の再計算を通します。各カードの数字はその時点の旅程に
  対する実測で、1件採用したら残りは組み直された旅程に対して測り直します。

### 7.2 食事

参照画像 03 の形。既定1件＋代替2件（`product.md` の
「one default and at most two alternatives」と一致）。既定には
「おすすめ」バッジ、代替には「代替案1 / 2」。

### 7.3 ホテル

受領物は明示的に **「Do not show lists」**、示すのは
**「This hotel fits this trip」** と書いています。
現行の `rankHotelCandidates` は全行程の移動時間で実ビルド比較しており、
`hotelRebaseIsWorthwhile` は「hard conflict 解消／60分以上短縮／15%以上短縮」
の閾値を持っています。**言うべきことはすでに計算済み**です。

表示は参照画像 03 の形に揃えます:
「おすすめ拠点 インターラーケン・オスト周辺 / **移動 −1時間20分** /
観光・移動のバランスが良いエリアです」。
候補一覧は既定では出さず、詳細側に置きます。
価格・お得さの表現は実際の価格シグナルがあるときだけ（`valueId` は
現在意図的に null。捏造しない）。

### 7.4 採用と取り消し

採用は楽観的挿入ではなく、これまで通り**日全体の再計算**を通します
（hard conflict を作らない／Anchor を後ろに追いやらない／予約を破らない）。
成功したらトーストで **「昼食を追加しました 余裕 −45分 元に戻す」**
（参照画像 03）。**帰結の数字を必ず出す**のが v3.1 の要求です。
Undo は既存の履歴操作を使います。

取得に失敗したときは、空の推薦枠を残さず、旅程の外側で一度だけ告知します
（現在の「昼食候補を取得できませんでした」行はタイムラインの中に
大きな空箱を作っており、Tier C に該当します）。

## 8. v3.1 が変更しないもの

明示しておかないと「簡素化」の名目で壊れる契約です。

1. 決定論スケジューラ・実現性判定・hard constraint 管理・推薦ランキングの
   権限（AI は言語生成のみ、順位付けは決定論コード）。
2. `docs/product.md` の v0.3 contract 全体。特に:
   ファーストビューが答える5つの問い、Anchor/Filler、1日あたりの
   Filler 上限（昼1・夕1・カフェ/微小1）、gap の帯（<30 なし / 30–59 /
   60–120 / それ以上は P0 外）、1日1 gap・最大の gap、
   ホテルのリベース閾値、地図契約。
3. モバイルの「旅程 or 地図」二択（参照画像 04 が追認）。
4. Gate A〜E（課金境界・旅程の真実性・Worker 信頼性・プライバシー・
   ファーストビュー契約）。
5. アクセシビリティ: WCAG 2.2 AA、タップ標的 44px（モバイルシート内 24px）、
   キーボードのみで完結、320px リフロー、200% ズーム。
   §4.3 の文字下限はこれを**強める**方向です。
6. 既存テストの削除・緩和は禁止。仕様変更が要るときは
   「なぜ変えるのか」「どの既存テストを変えるのか」を先に書く。

## 10. 判断に迷ったときの順序

1. それは利用者の行動を変えるか。変えないなら Tier B か C。
2. 数字を出すなら、その確度は言葉に載っているか（§2.2）。
3. その要素は既存の10コンポーネントのどれかに入るか。
4. `docs/product.md` の契約を弱めていないか。
5. 「I only entered places. The trip was already planned.」に近づくか。
