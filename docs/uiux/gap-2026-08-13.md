# 現状と v3.1 基準の差分（2026-08-13 実測）

基準は [`design-standard-v3.1.md`](design-standard-v3.1.md)。ここは
**いま何がどれだけ違うか**と**どの順で埋めるか**だけを書きます。
測定対象は `8e0a150`（branch `claude/architecture-v2`）の
VR ベースライン24枚と `app/planner.css` / `app/components/planner/**`。

---

## 0. 結論

**構造は合っている。壊れているのは密度と語彙です。**

受領物が要求する10コンポーネントは**全部すでに存在**し（基準 §5）、
モバイルの「旅程 or 地図」二択は参照画像が**追認**し、
デイパレット7色は `PLANNER_MAP_DAY_COLORS` と CSS で**すでに一致**し、
アクセントカラー `#d63f35` は参照画像の CTA と**ほぼ同色**です。

差は3つに集約されます。

1. **文字が小さすぎる** — `app/planner.css` の `font-size` 宣言 374件のうち
   **258件（69%）が 12px 未満**、うち61件が 10px 未満。
   参照画像の calm / premium はここで失われています。
2. **写真が無い** — 参照画像は全面的に写真主導。タイムラインの停留所行に
   写真が1枚もありません（パイプラインは存在する、基準 §3）。
3. **内部語彙が既定画面にある** — 「推定」バッジ、「条件付き」チップ、
   「未確認の重要情報が10件」、「実経路／推定」凡例、空の「おすすめ枠」。

## 3. 着手順

依存関係が1本あります。**Step 0 を先にやらないと、Step 1 は情報の消失に
なります。**

### Step 0 — 根拠の受け皿を作る

詳細シートに「営業時間・根拠を見る」を新設し、営業時間の取得結果と取得元・
滞在時間の確度・経路の実測／推定の別をその中に置く。
既定画面からは何も消さない（この時点では二重に出ている状態）。

- 対象: `inspector/StopInspector.tsx`
- リスク: 低。追加のみ。VR は detail-* 6枚が動く
- 仕様変更: なし

### Step 1 — 語彙と密度

基準 §2.2 の語彙置換、Tier C の削除、§4.3 のタイポスケール、
§4.4 の余白・角丸の整理、主 CTA を赤、余裕を緑。

- 対象: `lib/presentation/timeline-presentation.ts`, `app/planner.css`,
  `summary/ResultHeader.tsx`, `timeline/ActivityCard.tsx`
- リスク: 中。**VR 24枚すべてが動く**。Gate E の ratchet が効くので
  ファーストビュー契約は自動で守られる
- 仕様変更: あり（`docs/product.md` に「確度は語彙で運ぶ」を1段落追加）
- 影響する既存テスト: `tests/timeline-presentation.test.ts`（`durationSourceLabel`
  の期待値）、`tests/banned-terms.test.ts`（パターン追加）。
  **削除・緩和ではなく期待値の更新**として扱い、理由を明記する

### Step 2 — タイムラインの形

`ActivityCard` に写真・説明・新寸法、`MovementCard` のカード化、
日タブの塗りピル化。

- 対象: `timeline/ActivityCard.tsx`, `timeline/MovementCard.tsx`,
  `timeline/ItineraryTimeline.tsx`, `app/planner.css`
- リスク: 中〜高。**写真は課金経路**（`/api/place-photo`）なので、
  旅程1件あたりのリクエスト上限を決めて Gate A の予算に載せてから出す。
  ビルド時に取得済みの place intelligence だけを使い、写真のために
  新しい検索を起こさない
- 検証: E2E のタップ標的（44px / シート内24px）、写真取得失敗時に
  レイアウトが崩れないこと

### Step 3 — 結果画面の構造

feasibility カードと警告バンドをファーストビューから外す、
推薦を第3カラム／ボトムシートへ、採用トースト（帰結の数字＋Undo）。

- リスク: 高（`TripPlannerShell.tsx` は2343行）。Gate E は**緩む**方向
- 仕様変更: あり。`docs/product.md` の「ファーストビューが答える5つの問い」の
  **順序は維持**したまま、2番目（最重要の警告）の置き場所が変わる。
  変更理由と影響テストを先に書く

### Step 4 — 入力画面

チップ入力、旅程プレビュー、ステッパー廃止、CTA コピー。

- 対象: `start/*`
- リスク: 低〜中。start-* の VR 6枚

## 4. 先に決めておくべきこと

実装前に判断が要る2件です。どちらも技術ではなく**方針**の問題です。

1. **写真の課金予算。** 停留所ごとのサムネイルは `/api/place-photo` の
   従量課金です。旅程1件・1日分の表示で何枚まで許すか（例: 表示中の日の
   停留所のみ＝1日あたり最大4〜6枚）を決めないと、Step 2 は出せません。
2. **評価と営業状態を出すか。** 参照画像は「4.6★（512件）・営業中」を
   出しています。TripCheck は `rating` / `userRatingCount` を推薦候補では
   すでに取得済みですが、**Anchor（利用者自身の場所）については
   出す／出さないを決めていません**。出すなら実データのあるときだけ、
   というのが基準 §2.3 の要求です。

## 5. この差分で**やらないと決めた**こと

- **エンジンには触らない。** 実現性判定・スケジューラ・hard constraint・
  推薦ランキングは対象外です（基準 §8）。
- **左のアイコンレール（参照画像 02）は任意扱い。** 既存ヘッダー機能の
  移設であって、新しい情報を増やすものではないため、優先度は最低。
- **「ガイドブック」「予約」「費用サマリー」タブ（参照画像 02 / 03 の
  ヘッダー）は範囲外。** 実装が存在しない機能で、v3.1 は UI/UX の
  方向のみを定義する資料です。空のタブを作るのは、この製品が
  避けてきた「無いものを有るように見せる」ことに当たります。
