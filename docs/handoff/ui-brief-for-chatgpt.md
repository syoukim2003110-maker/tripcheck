# TripCheck 旅のしおりメーカー — UI/UX 改修の依頼書

見た目と使い勝手(UI/UX)の改修を担当してもらうための依頼書です。
作業の前に、リポジトリ直下の `AGENTS.md` を必ず読んでください。分担と、壊してはいけないものが書いてあります。

- 本番サイト: https://trip.hikakunoshiori.com/ja/
- 作業ブランチ: `claude/free-place-resolution`(`main` は古い別系統なので使わない)
- 今の画面の写真: `docs/handoff/current-ui/`
- すぐに「しおり」画面を開ける見本リンク: `docs/handoff/sample-trip-link.txt`

## 1. このサービスは何か

行きたい場所を選ぶだけで、そのまま使える「旅のしおり」ができるサイトです。
何日目にどこへ、どの順番で、どうやって移動するか(どの路線で、どこで乗り換えるか)、どこで食べるか、どこに泊まるかを、地図と一緒に出します。無料・登録なし。使う人は、旅行を計画している普通の人で、主にスマホで見ます。

画面は3つです。
1. **ホーム** — 行き先(街)を選ぶ
2. **場所を選ぶ** — その街の行きたい場所をタップで選ぶ。自分で店・ホテル・場所を検索して追加もできる
3. **しおり** — 日ごとの予定、移動、食事、ホテル、地図

## 2. 目指す見た目と使い心地

オーナーが近いと感じているのは、**Google、Apple、Airbnb、Adobe** の製品です。オーナーが添付する画像・サイトも参考にしてください。共通点を言葉にすると次のとおりです(解釈は任せます)。

- 余白が広く、一度に見せる情報が少ない。大事なものから順に目に入る
- 文字の大きさ・太さ・色の差で、見出しと補足がはっきり分かれている
- 色数が少なく、写真と中身が主役。飾りは控えめ
- 迷わない。次に何を押せばいいかが、説明を読まなくても分かる
- 触った反応が自然(押した、開いた、切り替わった、が気持ちよく伝わる)

今の画面は「紙の旅のしおり」風(明朝体の表紙、消印、スタンプ、切符の半券)です。**この世界観を残す必要はありません。** 上の方向に合うなら、置き換えて構いません。残すと良い要素があると思えば、理由を添えて残してください。

## 3. 今の画面の問題(オーナーの感じていること+現状の観察)

オーナーの言葉: 「情報を詰め込みすぎて見づらい」「見せ方や、サイトを使うときの動線に改善の余地が多い」。

写真(`docs/handoff/current-ui/`)と本番で見て、こちらで把握している具体例です。これ以外も、気づいたものは直してください。

**しおり画面**
- スマホで、最初の予定にたどり着くまでが長い。表紙、目次の図、ボタン4つ、日数、日付タブ、地図が先に並ぶ(`03-plan-phone-top.jpg`)
- 電車の移動1つに、要約・乗り継ぎの並び・徒歩の合計・駅までの徒歩・切符カード・乗り換え・駅からの徒歩・リンク2本が全部出ている。同じことを2回言っている部分がある(`06-plan-desktop-timeline.jpg`)
- PC幅で、移動の下のリンク2本がくっついて1行になっている(同じ写真の下部)
- 「目安」「約」などの注記、出典、説明文が多く、どれも同じ強さで目に入る
- 予定のカードを開くと、滞在時間の変更、日の変更、削除、営業時間、地図リンク、写真の出典が一度に出る(`08-place-card.jpg`)
- 昼ごはん・カフェの候補は、開くと長いリストがその場に広がり、予定の流れが途切れる
- 「場所の追加」と「泊まる場所」がページのいちばん下にあり、存在に気づきにくい
- 1日が長いと、ページがとても長くなる(`04-plan-phone-full.jpg` は1日目だけでこの長さ)
- 地図と予定の関係が弱い。地図で見ている場所と、下の予定が連動して見えにくい

**場所を選ぶ画面・ホーム**
- 選んだ数や、次に進むボタンは下の帯にあるが、「選ぶ → 日数を決める → 作る」の流れが一目では分からない
- 自分で店やホテルを追加する入口が、場所の一覧のずっと下にある
- ホームは写真のカードが並ぶだけで、このサイトで何ができるかが伝わりにくい

## 4. お願いしたいこと

**範囲:** 3つの画面すべての見た目と、画面内・画面間の動線。スマホを最優先、PC幅も整える。日本語と英語の両方。印刷したときの見た目(紙のしおり)も保つ。

**進め方(2段階):**

1. **まず方針を見せてください(コードを大きく変える前に)。**
   - 目指す方向を一言で
   - 3画面それぞれの「今 → こう変える」(スマホ幅の図や画面の写真。簡単なもので構いません)
   - 情報の整理の方針(何を最初から見せ、何を折りたたみ、何を消すか)
   - 色・文字・余白などの基本ルール
   オーナーが見て「この方向で」と言ってから、実装に進んでください。
2. **実装は小さく分けてコミット**してください(例: 基本ルール → しおり画面 → 場所を選ぶ画面 → ホーム → 印刷)。各コミットで、何を変えたかを一言で。

**変えてよいファイル:** `app/shiori/shiori.css`、および `app/shiori/ShioriApp.tsx` / `ShioriMap.tsx` / `PlaceCard.tsx` の中の見た目に関わる部分(HTML の構造、クラス名、文言の整理)。

**変えないもの:** `lib/`、`scripts/`、`deploy/`、`public/rail/`、`tests/`、`lib/security-headers.ts`。ボタンを押したときの動作、取得するデータ、数字の意味。見た目のために別のデータや動作が必要になったら、実装せずに「これが必要」と書き残してください(中身の担当が対応します)。

## 5. 必ず守ること(詳しくは AGENTS.md)

- **「目安」「約」「ごろ」を消さない・弱めない。** 時刻は時刻表ではなく計算上の目安です。運賃・運行間隔・番線・評価など、持っていない情報を足さない
- **ホットペッパーの表記は一字も変えない。** `【画像提供：ホットペッパー グルメ】` と `Powered by <a href="http://webservice.recruit.co.jp/">ホットペッパーグルメ Webサービス</a>`。掲載店や写真を出す場所と、ページ最下部に残す
- **地図の出典(OpenFreeMap / OpenStreetMap)を残す**
- **外部のフォント・スクリプト・画像・計測タグを新しく読み込まない。** 端末に入っているフォントか、`public/` に置いたファイルだけ(読み込み先はテストで固定されています)
- **使いやすさ:** キーボードで操作できる、押せる場所は44px以上、文字と背景の濃さの差(AA)、動きを減らす設定に従う、スマホ幅375pxで横にはみ出さない
- **文言は日本語・英語の両方**(`ShioriApp.tsx` の `text` に両方ある)
- **鍵には触れない。** `.env.local` と `dist-static/` は読まない・コピーしない・コミットしない

## 6. 手元での動かし方

```bash
pnpm install
pnpm dev
```

`http://localhost:3000/ja` を開きます(ポートは表示されたものに合わせてください)。`docs/handoff/sample-trip-link.txt` の1行を、アドレスの `/ja/` のあとに貼って開くと、ホテルと店が入った東京3日間のしおりがそのまま出ます。

鍵がない環境では、次の3つは「取得できませんでした」と出ます。壊れているのではありません。見た目は本番サイトと `current-ui` の写真で確認してください。
- 店・ホテル・場所の検索
- 昼ごはん・カフェ・ホテルの候補(写真と予算つきのリスト)
- 営業時間・電話のカード
